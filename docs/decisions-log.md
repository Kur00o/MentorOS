# Decisions Log (Architectural Decision Records)

Record key technical decisions made over the course of building MentorOS.

---

## ADR 1: Monorepo Strategy
- **Status**: Approved
- **Context**: The build requires simultaneous contributions from 3 independent pairs of developers targeting frontend interfaces, scoring calculations, and AI companions.
- **Decision**: Consolidate frontend, backend, and documentation in a single repository.
- **Consequence**: Dramatically reduces cross-repository dependency management and simplifies CI/CD pipeline integration.

---

## ADR 2: Feature-Based backend Directory Layout
- **Status**: Approved
- **Context**: Standard layer-based packaging (e.g. all routers in one folder, all services in another) causes merge conflicts and overlapping folder concerns between teams.
- **Decision**: Structure the `/backend/app/` subdirectory by domain/feature folders (`auth/`, `students/`, `scoring/`, `mentoring/`, `companion/`, `admin/`).
- **Consequence**: Teams A, B, and C can work in parallel inside their own files, reducing merge friction.

---

## ADR 3: Supabase is the system of record; the API is the only data path
- **Status**: Approved (consolidation, Nov 2026)
- **Decision**: Supabase Postgres (provisioned through Vercel Storage) is the primary store, Supabase Auth issues identities, Supabase Storage holds avatars/resumes. All reads and writes go through FastAPI, which resolves roles from the `users` table. RLS is enabled on every table with no policies and `anon`/`authenticated` grants are revoked, so PostgREST exposes nothing.
- **Consequence**: one enforcement point for permissions (admin → all, HOD → department, mentor → mentees, student → self); the legacy local-password login and auto-created student profiles were removed. Accounts are admin-provisioned only.

## ADR 4: One Vercel project for SPA + FastAPI; no Celery in the hosted stack
- **Status**: Approved
- **Decision**: Serve the API as a Vercel Python function in `bom1` (next to the Supabase `ap-south-1` database) and the SPA as static output from the same origin. Nightly recomputation runs through Vercel Cron; imports recompute synchronously. Celery remains optional for self-hosting.
- **Consequence**: no CORS in production, one deploy, ~250 ms DB round-trips; batch work stays well inside the 60 s function limit.

## ADR 5: Attendance pillar uses the raw percentage
- **Status**: Approved
- **Context**: The phase-3 engine mapped any attendance ≥ 80 % to 100, which contradicted the faculty-agreed `docs/scoring.md` ("directly maps to the raw attendance percentage") and the frontend replicated it.
- **Decision**: Follow the documented formula: attended ÷ held across all subjects (weighted by classes). One pure implementation (`backend/app/scoring/formula.py`) is shared by engine, simulator, seed and tests.

## ADR 6: Grounded AI Companion with optional LLM voice
- **Status**: Approved
- **Decision**: The companion always builds a grounded answer from role-scoped data plus a BM25 knowledge base; an LLM (Anthropic/OpenAI/Gemini/Ollama) may rephrase it but never adds facts. Replaces the Ollama + pgvector prototype, which required a self-hosted model.
- **Consequence**: works on serverless hosting with no API key; adding a key upgrades tone without changing correctness.

## ADR 7: Provenance-tagged synthetic data
- **Status**: Approved
- **Decision**: Every table carries `is_synthetic` and `batch_id` (→ `data_batches`). The demo institution uses `DEMO…` USNs and the reserved `mentoros.demo` domain, is generated deterministically from behavioural archetypes, and is scored by the real engine. It can be purged in one action by an institutional (non-demo) admin.

## ADR 8: Fresh Alembic baseline
- **Status**: Approved
- **Decision**: The hosted database is new, so the five team migrations were replaced by one autogenerated baseline (`0001_core`) that matches the consolidated models; earlier revisions remain in git history. Future changes are additive revisions; CI verifies `alembic upgrade head` on Postgres.
